# 测试设计文档

## 1. 测试目标

测试目标不是追求大而全，而是保证一天内上线版本的核心闭环稳定：

```text
语音或文字输入
-> Agent 理解
-> 用户确认
-> 日历操作
-> 视图更新
-> 本地持久化
```

高风险能力必须重点测试：

- 中文时间解析。
- 修改和删除事件匹配。
- 写入前确认。
- 语音失败后的兜底。
- 数据刷新后仍存在。

## 2. 测试分层

### 单元测试

重点测纯逻辑：

- 时间解析。
- 意图识别。
- 事件查询。
- 冲突检测。
- 撤销逻辑。

推荐工具：

- Vitest。

### 组件测试

重点测交互组件：

- 语音输入面板。
- 确认卡片。
- 日历事件列表。
- 事件详情面板。

可选工具：

- React Testing Library。

第一版时间紧时可以少做组件测试，但确认卡片建议至少手工覆盖。

### 端到端测试

重点测完整用户路径：

- 添加事件。
- 查询事件。
- 修改事件。
- 删除事件。
- 刷新后持久化。

可选工具：

- Playwright。

第一版如果时间紧，可以用手工验收清单替代自动化 E2E。

### 手工测试

语音能力必须手工测试：

- 浏览器权限。
- 识别准确度。
- 噪音环境。
- 识别失败提示。
- 文字兜底。

## 3. 测试优先级

### P0：必须测试

- 添加日程。
- 查询日程。
- 修改日程。
- 删除日程。
- 删除二次确认。
- 刷新后数据仍在。
- 语音不可用时文字输入可用。
- 空输入、无法理解输入不崩溃。

### P1：建议测试

- 冲突检测。
- 撤销。
- 空闲时间查询。
- 示例指令。
- 移动端布局。
- 语音播报。

### P2：有时间再测

- ICS 导出。
- AI 解析接口。
- 多浏览器兼容。
- 大量事件性能。

## 6. 日历操作测试用例

### 新增

前置条件：

- 日历为空。

操作：

- 添加明天下午 3 点产品评审会。

期望：

- 事件列表新增 1 条。
- 标题正确。
- 时间正确。
- 提醒正确。
- localStorage 中存在该事件。

### 删除

前置条件：

- 已存在产品评审会。

操作：

- 输入删除指令。
- 点击确认。

期望：

- 事件被删除。
- lastAction 可撤销。
- 刷新后事件不出现。

### 修改

前置条件：

- 已存在下午 3 点产品评审会。

操作：

- 输入「把产品评审会改到下午四点」。
- 确认。

期望：

- 原事件时间更新到 16:00。
- 不创建重复事件。

### 查询

前置条件：

- 今天、明天、本周各有事件。

操作：

- 输入「我明天有什么安排」。

期望：

- 只返回明天事件。
- 今日事件不混入。

## 7. 语音测试

测试环境：

- Chrome 最新版。
- 麦克风可用。
- 桌面端优先。

测试点：

- 点击麦克风能请求权限。
- 用户说话时有 listening 状态。
- 停止后识别文本出现在输入区。
- 用户可编辑识别文本。
- 提交后进入 Agent 解析。
- 拒绝权限时给出提示，不影响文字输入。

## 8. 确认机制测试

所有写操作都必须出现确认卡片：

- create_event。
- update_event。
- delete_event。
- conflict_continue。

确认卡片必须包含：

- 操作类型。
- 事件标题。
- 时间。
- 提醒。
- 确认按钮。
- 取消按钮。

删除操作额外要求：

- 文案明确提示这是删除操作。
- 不允许一句删除指令直接执行。

## 9. 回归测试清单

每次大改后至少跑：

- [ ] 添加明天下午三点事件。
- [ ] 查看明天安排。
- [ ] 修改事件到下午四点。
- [ ] 删除事件并确认。
- [ ] 撤销删除。
- [ ] 刷新页面，事件仍存在。
- [ ] 语音不可用时文字输入正常。
- [ ] 空输入不报错。
- [ ] 无法理解输入有提示。

- [ ] 文字兜底流程通过。

- [ ] 控制台无阻断性错误。
- [ ] 线上预览地址可访问。

## 11. 测试结论

第一版测试重点应该放在 Agent 和日历状态一致性上。

语音识别本身依赖浏览器，不需要过度自动化，但必须有清晰兜底。只要文字指令完整闭环稳定，语音层即使出现权限问题，也不会导致作品无法演示。
