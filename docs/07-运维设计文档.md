# 运维设计文档

## 1. 运维目标

语音日历 Agent 第一版的运维目标是：低成本、低依赖、可快速上线、可快速回滚。

核心原则：

- 第一版优先静态部署。
- 不引入必须长期维护的服务器。
- 不把 AI API、数据库、第三方日历作为上线硬依赖。
- 保证演示环境稳定，失败时有文字输入兜底。

## 2. 部署形态

### 第一版：纯前端静态部署

```text
用户浏览器
  -> 静态前端资源
  -> Web Speech API
  -> localStorage
```

推荐平台：

- Vercel
- Netlify
- Cloudflare Pages
- GitHub Pages

优势：

- 部署快。
- 回滚简单。
- 无服务器运维。
- 不需要数据库迁移。
- 演示稳定性高。

### 第二版：静态前端 + Serverless AI 代理

```text
用户浏览器
  -> 静态前端
  -> /api/parse-command
  -> AI Provider
```

适用场景：

- 需要保护 AI API Key。
- 需要提升复杂自然语言解析能力。
- 需要记录匿名解析质量日志。

### 第三版：完整服务端

```text
用户浏览器
  -> 应用后端
  -> 数据库
  -> 第三方日历 API
  -> 定时提醒任务
```

适用场景：

- 用户登录。
- 多端同步。
- 云端提醒。
- Google Calendar / Outlook 集成。

第一版不建议进入第三版形态。

## 3. 环境划分

### local

用途：

- 本地开发。
- 语音识别调试。
- Agent 解析测试。

特点：

- 使用本地 localStorage。
- AI 接口默认关闭。

### preview

用途：

- 每次提交后的预览环境。
- 给团队和评委提前试用。

特点：

- 可使用演示数据。
- 可开启调试日志。

### production

用途：

- 正式演示和上线。

特点：

- 默认关闭敏感日志。
- 保留文字输入兜底。
- 页面提供示例指令。

## 4. 构建与发布流程

推荐流程：

```text
本地开发
-> npm run test
-> npm run build
-> 部署 preview
-> 手工跑演示脚本
-> 部署 production
-> 保留上一个可用版本作为回滚点
```

最小命令：

```text
npm install
npm run dev
npm run test
npm run build
```

如果时间紧张，至少必须执行：

```text
npm run build
```

## 5. 配置管理

第一版推荐环境变量：

```text
VITE_APP_NAME=Voice Calendar Agent
VITE_ENABLE_AI_PARSE=false
VITE_AI_PROVIDER=
VITE_AI_BASE_URL=
VITE_AI_MODEL=
```

注意：

- 不要在前端公开真实 AI API Key。
- 如果必须演示 AI 能力，用本地 `.env.local`，不要提交。
- 生产环境如需 AI，必须走 Serverless 代理。

## 6. 日志设计

第一版只需要前端日志，不上传用户隐私数据。

可记录：

- 语音识别是否可用。
- Agent 意图类型。
- 解析是否成功。
- 是否触发降级。
- 操作是否确认。

不建议记录：

- 用户完整日程内容。
- 语音原文。
- 个人地点、参与人等敏感信息。

调试模式下可以在浏览器控制台输出详细日志，生产模式默认关闭。

## 7. 监控设计

第一版轻量监控即可：

- 页面是否能打开。
- 构建是否成功。
- 浏览器控制台是否有致命错误。
- 语音识别是否进入可用状态。

如果接入线上监控，建议只采集：

- 页面错误。
- 资源加载失败。
- API 调用失败。
- 解析失败计数。

不要采集用户日程原文。

## 8. 数据备份与恢复

第一版本地数据存储在 localStorage。

风险：

- 用户清理浏览器数据会丢失。
- 换设备无法同步。

应对：

- 提供一键导出 JSON。
- 可选提供导入 JSON。
- 后续支持 ICS 导出。

第一版至少可以实现：

- 演示数据重置。
- 清空本地数据。
- 导入 / 导出作为加分项。

## 9. 回滚策略

静态部署平台通常支持版本回滚。

回滚触发条件：

- 页面白屏。
- 构建资源加载失败。
- 核心添加日程流程不可用。
- 语音失败且文字输入也不可用。

回滚方式：

- Vercel / Netlify 控制台回滚到上一版本。
- 或重新部署上一版构建产物。

## 10. 运维风险与预案

| 风险 | 表现 | 预案 |
| --- | --- | --- |
| 麦克风权限失败 | 无法语音输入 | 文字输入兜底 |
| Web Speech API 不可用 | 浏览器不支持语音识别 | 提示使用 Chrome；保留文字输入 |
| localStorage 被清空 | 事件丢失 | 演示数据一键恢复；后续支持导出 |
| AI 接口失败 | 复杂指令解析失败 | 本地规则解析兜底 |
| 部署失败 | 无法访问线上地址 | 本地演示；保留上一版本 |
| 静态资源缓存 | 用户看到旧版本 | 部署平台自动 hash；必要时刷新缓存 |

## 11. 上线检查清单

- [ ] `npm run build` 成功。
- [ ] 首屏无白屏。
- [ ] Chrome 中语音权限可申请。
- [ ] 文字输入可用。
- [ ] 添加事件可用。
- [ ] 删除事件有确认。
- [ ] 刷新页面事件不丢失。
- [ ] 示例指令可点击。
- [ ] 演示数据可重置。
- [ ] 生产环境没有暴露 API Key。

## 12. 运维结论

第一版采用静态前端部署最合适。

不要为了“系统完整”过早引入：

- 自建服务器。
- 云数据库。
- 登录系统。
- 第三方日历 OAuth。
- 后台管理系统。

这些会显著增加运维复杂度，不利于一天内上线。
