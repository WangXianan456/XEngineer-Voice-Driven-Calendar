# 前端设计文档

## 1. 设计目标

前端要承担这个产品最重要的体验：让用户感觉自己是在和一个懂日历的语音 Agent 协作，而不是在填传统日历表单。

核心目标：

- 首屏能立刻看出这是语音日历工具。
- 语音输入是主入口，文字输入是稳定兜底。
- Agent 的理解结果必须可见、可确认、可修正。
- 日历视图必须和对话状态实时联动。
- 一天内能开发、测试、部署。

## 2. 第一轮思考：如果做成普通日历

最直接的方案是做一个传统日历页面：

- 月历视图。
- 新建事件弹窗。
- 事件列表。
- 删除和编辑按钮。

问题：

- 这类产品已经很多，不能突出题目里的「语音版」和「Agent」。
- 用户仍然需要手动填写标题、时间、提醒。
- 评委看不出语音交互带来的效率提升。

结论：

普通日历只能作为底层能力，不能作为主体验。

## 3. 第二轮思考：如果做成聊天机器人

另一个方案是做成聊天窗口：

- 用户说一句话。
- Agent 回复一句话。
- 后台更新日历。

问题：

- 容易变成普通聊天 Demo。
- 日历状态不可视，用户不知道事件是否真的写入。
- 删除、修改等高风险操作缺少空间展示确认信息。

结论：

聊天是 Agent 交互的一部分，但不能只做聊天。必须有日历工作台。

## 4. 第三轮思考：语音日历工作台

最终采用「语音 Agent + 日历工作台」的设计。

页面分成四个核心区域：

- 语音指令区：麦克风、识别文本、文字输入兜底。
- Agent 确认区：展示理解结果、追问、确认、取消。
- 日历视图区：今日、本周、月历或周历。
- 事件详情区：展示选中事件、提醒、来源语音、操作按钮。

这个方案的优势：

- 语音是第一入口。
- 日历状态可视。
- Agent 决策过程透明。
- 删除、修改前能做强确认。
- 开发复杂度仍然可控。

## 5. 页面信息架构

### 桌面端布局

```text
+------------------------------------------------------+
| 顶部栏：产品名 / 当前日期 / 语音状态 / 设置          |
+----------------------+-------------------------------+
| 语音 Agent 区        | 日历视图区                    |
| - 麦克风按钮         | - 今日安排                    |
| - 识别文本           | - 本周列表                    |
| - 文字输入           | - 简单月历                    |
| - 对话记录           |                               |
| - 确认卡片           |                               |
+----------------------+-------------------------------+
| 事件详情 / 示例指令 / 最近操作                       |
+------------------------------------------------------+
```

推荐桌面端：

- 左侧 36%：语音 Agent。
- 右侧 64%：日历和事件列表。
- 底部或右侧抽屉：事件详情。

### 移动端布局

```text
+-------------------------------+
| 顶部栏                         |
+-------------------------------+
| 大麦克风按钮                   |
| 识别文本 / 输入框              |
+-------------------------------+
| Tabs：今天 / 本周 / 对话        |
+-------------------------------+
| 对应内容                       |
+-------------------------------+
```

移动端优先保证：

- 麦克风按钮足够明显。
- 文字不重叠。
- 确认按钮容易点击。
- 日程列表比月历更重要。

## 6. 核心组件设计

### VoiceCommandPanel

职责：

- 控制录音状态。
- 展示语音识别结果。
- 提供文字输入兜底。
- 提交自然语言指令给 Agent。

状态：

- `idle`：未录音。
- `listening`：正在听。
- `transcribing`：识别中。
- `error`：语音不可用。

### AgentConversation

职责：

- 展示用户指令和 Agent 回复。
- 展示追问。
- 管理确认卡片。
- 支持用户说「确认」「取消」「撤销」。

消息类型：

- `user_text`
- `agent_text`
- `confirmation`
- `error`
- `system`

### ConfirmationCard

职责：

- 写入日历前展示结构化结果。
- 删除和修改前做二次确认。
- 对冲突事件做提示。

展示字段：

- 操作类型。
- 事件标题。
- 开始时间。
- 结束时间。
- 提醒。
- 冲突提示。
- 确认 / 取消按钮。

### CalendarWorkspace

职责：

- 展示今日安排。
- 展示本周安排。
- 展示简单月历。
- 支持点击事件查看详情。

第一版不追求复杂拖拽，优先确保状态清晰。

### EventDetailPanel

职责：

- 展示事件详情。
- 支持编辑、删除、撤销。
- 展示来源语音，体现 Agent 能力。

### ExampleCommands

职责：

- 展示可点击示例指令。
- 降低用户首次使用成本。
- 保证评委能快速触发核心能力。

示例：

- 明天下午三点开产品评审会，提前十分钟提醒我。
- 我明天有什么安排？
- 把产品评审会改到下午四点。
- 删除明天的产品评审会。
- 明天下午我什么时候有空？

## 7. 前端状态设计

### 全局状态

```ts
type AppState = {
  events: CalendarEvent[];
  selectedEventId?: string;
  messages: AgentMessage[];
  pendingAction?: PendingCalendarAction;
  lastAction?: UndoableAction;
  speechStatus: SpeechStatus;
  activeView: "today" | "week" | "month";
};
```

### 状态流转

新增事件：

```text
用户语音
-> 识别文本
-> Agent 解析
-> pendingAction
-> ConfirmationCard
-> 用户确认
-> 写入 events
-> 更新日历视图
-> Agent 反馈
-> 语音播报
```

删除事件：

```text
用户语音
-> Agent 查找候选事件
-> 0 个：提示未找到
-> 1 个：展示删除确认
-> 多个：展示候选选择
-> 用户确认
-> 删除事件
-> 保存 lastAction
-> 支持撤销
```

## 8. 交互细节

### 语音按钮

- 未录音：显示麦克风图标。
- 录音中：显示停止图标和动态状态。
- 语音不可用：显示禁用状态，但保留文字输入。

### 确认机制

所有写操作都必须确认：

- 新增事件。
- 修改事件。
- 删除事件。
- 冲突情况下继续添加。

确认可以通过按钮，也可以通过语音「确认」「取消」。

### 追问机制

当缺少关键信息时，不进入确认，而是追问：

- 缺少时间：「请问安排在什么时候？」
- 缺少标题：「请问这个日程叫什么？」
- 上午下午不明确：「你说的是上午还是下午？」

### 错误提示

错误提示要短，不暴露技术细节：

- 「我没有听清楚，可以再说一遍，或直接输入文字。」
- 「我还不能确定具体时间，请补充日期和时间。」
- 「没有找到匹配的日程。」

## 9. 视觉设计方向

风格关键词：

- 清晰。
- 工作台。
- 可信。
- 高效。

避免：

- 做成营销落地页。
- 大面积装饰图。
- 只有聊天框。
- 卡片套卡片。

颜色建议：

- 背景使用中性浅色。
- 主操作使用清晰蓝色或绿色。
- 删除使用红色。
- 冲突使用橙色。
- 日历事件用不同颜色区分类型，但不要过度花哨。

## 11. 前端验收标准

- 首屏能看到麦克风、指令输入、日历安排。
- 不开麦克风也能用文字完整演示。
- 添加事件前展示结构化确认。
- 删除事件前必须二次确认。
- 事件增删改后日历视图实时更新。
- 刷新页面后本地事件不丢失。
- Chrome 中语音识别可用。
- 移动端无明显文字重叠。
