# 后端设计文档

## 1. 设计目标

后端设计的核心不是一开始就做重型服务，而是明确哪些能力需要后端、哪些能力可以先放在前端，并为后续扩展留下清晰边界。

一天内上线目标：

- 第一版可以没有自建后端。
- 如果接入 AI API，需要一个轻量代理服务保护密钥。
- 日历核心能力先在前端本地完成，避免账号、数据库、OAuth 拖慢上线。
- 架构上预留后端工具调用接口，后续能接入真实日历和云端同步。

## 2. 第一轮思考：完全无后端

方案：

- 语音识别使用浏览器 Web Speech API。
- Agent 基础解析在前端完成。
- 日历数据存 localStorage。
- 静态部署即可上线。

优点：

- 开发最快。
- 部署最简单。
- 不需要数据库。
- 不需要服务器运维。
- 不需要处理登录和权限。

问题：

- 无法保护 AI API Key。
- 不能多端同步。
- 不能接入真实第三方日历。
- 数据只存在当前浏览器。

结论：

适合一天内 MVP，但需要设计好未来后端边界。

## 3. 第二轮思考：完整后端

方案：

- 用户登录。
- 服务端数据库。
- AI 解析服务。
- Google Calendar / Outlook 同步。
- 云端提醒任务。

优点：

- 更像真实产品。
- 数据可同步。
- 可以保护密钥。
- 可以接第三方日历。

问题：

- 开发量大。
- OAuth 和权限调试耗时。
- 部署复杂度增加。
- 一天内很容易做不稳定。

结论：

完整后端不适合作为第一版主线，可以作为后续路线图。

## 4. 第三轮思考：轻后端可插拔方案

最终建议：

- 第一版默认纯前端。
- 如果要用 AI，增加一个最小后端代理接口。
- 后端只做 AI 转发和可选日志，不承担日历主状态。
- 日历工具接口保持抽象，未来可以替换为云端 API。

这样能兼顾：

- 一天内上线。
- AI Key 不暴露。
- 未来可扩展。
- 当前功能不被后端阻塞。

## 5. 后端能力分层

### 第一阶段：无后端

```text
浏览器
  -> Web Speech API
  -> 前端规则解析
  -> localStorage 日历数据
  -> 前端日历视图
```

适合：

- Demo。
- 本地部署。
- 无账号版本。

### 第二阶段：AI 代理后端

```text
浏览器
  -> /api/parse-command
  -> AI Provider
  -> 返回结构化 JSON
  -> 前端确认
  -> 前端写入 localStorage
```

适合：

- 提升复杂口语理解。
- 保护 API Key。
- 保留本地日历闭环。

### 第三阶段：云日历后端

```text
浏览器
  -> 应用后端
  -> 数据库
  -> 第三方日历 API
  -> 提醒任务
```

适合：

- 多端同步。
- 真实用户账号。
- 第三方日历集成。

## 6. 最小后端接口设计

如果实现后端，第一版只建议做一个接口。

### POST /api/parse-command

用途：

把用户自然语言指令解析成结构化日历操作。

请求：

```json
{
  "text": "明天下午三点开产品评审会，提前十分钟提醒我",
  "locale": "zh-CN",
  "timezone": "Asia/Shanghai",
  "now": "2026-05-30T22:30:00+08:00",
  "calendarContext": {
    "recentEvents": [],
    "selectedEvent": null
  }
}
```

响应：

```json
{
  "intent": "create_event",
  "confidence": 0.92,
  "action": {
    "type": "create_event",
    "title": "产品评审会",
    "start": "2026-05-31T15:00:00+08:00",
    "end": "2026-05-31T16:00:00+08:00",
    "reminderMinutes": 10,
    "location": "",
    "notes": ""
  },
  "missingFields": [],
  "reply": "我理解的是明天下午三点到四点的产品评审会，提前十分钟提醒。是否确认？"
}
```

失败响应：

```json
{
  "intent": "unknown",
  "confidence": 0.2,
  "action": null,
  "missingFields": ["start"],
  "reply": "我还不能确定具体时间，请补充日期和时间。"
}
```

## 7. AI 代理服务设计

职责：

- 保存 AI API Key。
- 调用 AI Provider。
- 约束输出 JSON。
- 做超时和错误处理。
- 返回前端可消费的结构化结果。

不负责：

- 直接写入日历。
- 直接删除事件。
- 跳过用户确认。

关键原则：

- 后端只给建议，前端负责确认和执行。
- AI 输出不能直接作为事实写入。
- 解析失败要降级到本地规则。

## 8. Prompt 设计

系统要求：

```text
你是一个日历指令解析器。请把用户中文自然语言解析成严格 JSON。
只输出 JSON，不要输出 Markdown。
如果信息不足，请填写 missingFields。
不要编造时间、标题、地点。
所有时间使用 ISO 8601，时区使用 Asia/Shanghai。
```

意图枚举：

```text
create_event
list_events
update_event
delete_event
find_free_time
set_reminder
confirm
cancel
unknown
```

安全规则：

- 删除事件只返回候选和建议，不直接执行。
- 修改事件只返回目标匹配条件和新字段，不直接执行。
- 时间不明确时必须追问。
- 置信度低于 0.7 时必须要求确认或补充。

## 9. 数据库设计，后续版本

第一版不需要数据库。后续如果做云端同步，可以使用以下结构。

### users


### calendar_events

```text

```

### agent_actions

```text

```

用途：

- 追踪 Agent 解析质量。
- 支持撤销和审计。
- 分析用户常用指令。

## 10. 权限与安全

第一版安全边界：

- 不上传用户日历数据。
- 不保存用户账号。
- AI 接口可关闭。
- 所有写操作必须确认。

如果接入后端，需要：

- API Key 只存在服务器环境变量中。
- 前端不暴露真实密钥。
- 限制 AI 代理接口请求频率。
- 请求体限制长度。
- 不记录敏感原文，或提供关闭日志选项。

## 11. 部署方案

### 纯前端部署

推荐：

- Vercel。
- Netlify。
- Cloudflare Pages。

特点：

- 构建快。
- 不需要服务器。
- 最适合一天内上线。

### 带 AI 代理部署

推荐：

- Vercel Serverless Functions。
- Netlify Functions。
- Cloudflare Workers。

环境变量：

```text
AI_PROVIDER=openai
AI_API_KEY=your_key
AI_MODEL=gpt-4.1-mini
AI_BASE_URL=https://api.openai.com/v1
```

## 12. 后端验收标准

如果不做后端：

- 应用能纯前端完整运行。
- 语音、规则解析、日历 CRUD 均可用。
- 不需要任何服务端配置。

如果做 AI 代理：

- `/api/parse-command` 能返回严格 JSON。
- AI 超时后前端能降级到规则解析。
- 前端不暴露 API Key。
- 写入类操作仍然需要用户确认。
- 构建和部署不依赖本地私有配置。

## 13. 最终建议

第一天开发采用：

```text
纯前端主线 + 可选 AI 代理接口
```

具体执行：

1. 先实现前端规则解析和 localStorage 日历。
2. 再预留 `/api/parse-command` 调用封装。
3. 如果时间充足，再实现轻量 AI 代理。
4. 不在第一版接 Google Calendar、Outlook、数据库和登录。

这个后端设计的重点是把复杂度延后，但不把扩展路线堵死。
