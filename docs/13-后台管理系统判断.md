# 后台管理系统判断

## 1. 问题

语音日历系统是否需要做一个后台管理系统？

结论：

> 第一版不建议做独立后台管理系统。建议做一个内置的开发/演示调试面板，后台管理系统放到后续版本。

## 2. 为什么第一版不做后台管理系统

### 题目核心不是后台

题目要求是：

- 了解用户在日历管理中的真实需求。
- 设计并实现语音交互为核心的日历管理工具。
- 能通过语音添加、删除、查看事件提醒。
- 一天内开发上线。

评审重点会在：

- 语音交互是否顺畅。
- 日程理解是否准确。
- 增删改查是否完整。
- 体验是否可信。

后台管理系统不会直接增强这些核心指标。

### 后台会显著扩大范围

做后台通常意味着：

- 登录系统。
- 权限管理。
- 用户列表。
- 日程数据管理。
- 操作日志。
- 数据库。
- 服务端接口。

这些会占用大量开发时间，容易影响主应用完成度。

### 第一版数据在本地

第一版建议使用 localStorage 存储日程。

既然没有用户账号、云端数据库和多租户数据，就没有真正需要后台管理的对象。

## 3. 第一版应该做什么

不做独立后台，但可以做一个「调试/演示面板」。

建议名称：

- Debug Panel
- 演示控制台
- 开发者面板

位置：

- 主界面右上角设置按钮。
- 或页面底部折叠区域。

功能：

- 一键填充演示数据。
- 清空本地数据。
- 导出本地事件 JSON。
- 导入本地事件 JSON。
- 查看最近 Agent 解析结果。
- 开关语音播报。
- 开关 AI 解析。
- 查看浏览器语音支持状态。

这些功能服务于演示和开发，不是完整后台。

## 4. 后续什么时候需要后台

当产品进入真实用户使用阶段，才需要后台管理系统。

触发条件：

- 支持用户注册登录。
- 日历数据存到云端。
- 需要管理员查看系统使用情况。
- 需要管理 AI 调用成本。
- 需要查看错误日志和解析失败统计。
- 需要管理第三方日历授权。
- 需要客服排查用户问题。

## 5. 后续后台功能范围

如果后续做后台，可以包含：

### 用户管理

- 用户列表。
- 用户状态。
- 注册时间。
- 最近活跃时间。

### 日历数据管理

- 查看用户事件数量。
- 不直接展示敏感日程内容，除非用户授权。
- 支持数据删除请求。

### Agent 质量监控

- 意图识别成功率。
- 时间解析失败率。
- 用户取消确认比例。
- 高频无法理解指令。

### AI 成本管理

- 调用次数。
- Token 消耗。
- 失败率。
- 模型配置。

### 系统配置

- 是否启用 AI 解析。
- 默认模型。
- 语音能力开关。
- 示例指令配置。

### 安全与审计

- 管理员登录。
- 操作日志。
- 权限角色。

## 6. 第一版替代方案：演示控制台

建议第一版实现轻量演示控制台，而不是后台。

### 功能清单

P0：

- 一键填充演示数据。
- 清空本地数据。
- 查看 Web Speech API 是否可用。
- 查看当前事件数量。

P1：

- 导出 JSON。
- 导入 JSON。
- 查看最近 5 次 Agent 解析结果。
- 开关语音播报。

P2：

- 开关 AI 解析。
- 显示 AI 解析耗时。
- 显示规则解析命中情况。

### 价值

- 帮助现场演示。
- 帮助开发调试。
- 不引入用户系统和数据库。
- 不影响主线开发。

## 7. 决策建议

最终建议：

```text
第一版：不做后台管理系统
第一版：做内置演示控制台
后续版：有用户、云端数据和 AI 成本后再做后台
```

开发优先级：

1. 语音日历主应用。
2. Agent 解析和确认。
3. 日历 CRUD。
4. 演示控制台。
5. 后台管理系统规划。

不要让后台管理系统抢占第一版核心体验的时间。
