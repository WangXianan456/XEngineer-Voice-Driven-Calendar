# 决策记录

## 记录规则

本文件记录开发过程中的关键工程决策，避免后续编码偏离目标。

每条记录包含：

- 决策。
- 原因。
- 影响。
- 后续调整条件。

## ADR-001：第一版采用纯前端主线

决策：

第一版采用 React + Vite + TypeScript 的纯前端应用作为主线。

原因：

- 题目要求一天内上线。
- 语音识别可以使用浏览器能力。
- 日历数据可以先用 localStorage。
- 不引入服务器可以显著降低部署和调试成本。

影响：

- 第一版不支持多端同步。
- 第一版不支持账号体系。
- 第一版数据保存在当前浏览器。

调整条件：

- 需要保护真实 AI API Key。
- 需要多用户云端数据。
- 需要第三方日历同步。

## ADR-002：AI 解析作为增强，不作为硬依赖

决策：

本地规则解析是默认能力，AI 接口只作为复杂自然语言解析增强。

原因：

- AI API 可能受密钥、网络、成本影响。
- 评审演示必须保证离线或弱网络下仍可跑通。
- 高频日程指令可以用规则覆盖。

影响：

- 第一版优先实现中文时间和意图规则。
- AI 接口封装为可插拔模块。

调整条件：

- 基础闭环完成且有稳定 API Key。

## ADR-003：第一版不做独立后台管理系统

决策：

第一版不做独立后台管理系统，只做可选的内置演示控制台。

原因：

- 后台系统不直接提升语音日历核心体验。
- 后台会引入登录、权限、数据库和服务端接口。
- 一天内上线应优先保证主应用完整度。

影响：

- 演示数据、清空数据、调试信息放在前端控制台或演示面板。

调整条件：

- 后续引入用户、云端数据、AI 成本管理或运营需求。

## ADR-004：先实现文字指令闭环，再接语音

决策：

开发顺序先做文字指令 Agent 和日历 CRUD，再接 Web Speech API。

原因：

- 语音识别不稳定，不能作为第一条调试链路。
- 文字指令能快速验证 Agent 解析和日历状态。
- 语音层可以作为输入方式替换，不影响核心逻辑。

影响：

- 第一阶段先做 UI 和状态结构。
- 第二阶段先打通文字输入。
- 语音能力在核心逻辑稳定后接入。

调整条件：

- 基础 CRUD 和确认状态机完成。

## ADR-005：所有写操作必须确认

决策：

新增、修改、删除、冲突继续添加都必须经过确认。

原因：

- 日历是高信任工具。
- 语音识别和自然语言解析都存在不确定性。
- 删除和修改误操作会严重影响用户信任。

影响：

- 需要实现 `pendingAction` 状态。
- 对话区必须支持确认和取消。
- 删除操作必须二次确认。

调整条件：

- 后续可为低风险操作提供用户可配置的快捷确认，但默认仍应确认。
