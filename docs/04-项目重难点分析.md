# 项目重难点分析

## 1. 总体判断

语音日历 Agent 的难点不在做一个日历页面，也不在放一个麦克风按钮，而在于：

```text
把用户模糊、口语化、上下文相关的语音指令
稳定转换成可信的日历操作
```

核心挑战集中在：

- 中文自然语言时间解析。
- Agent 意图识别和多轮追问。
- 修改 / 删除时的事件匹配。
- 写操作确认和撤销。
- 语音识别不稳定时的兜底。
- 日历状态和对话状态一致性。
- 一天内控制范围并完成上线。

## 2. 难点一：中文自然语言时间解析

### 难在哪里

用户不会按标准格式输入时间，而会说：

- 明天下午三点。
- 后天上午十点半。
- 下周一早上。
- 今天晚上八点。
- 下午三点半。
- 提前十分钟提醒。
- 一小时后提醒我。

这些表达存在几个问题：

- 日期是相对的，需要结合当前日期。
- 上午、下午、晚上会影响小时数。
- 用户经常省略年份、月份、结束时间。
- 「三点」可能缺少上午 / 下午。
- 下周、周末、明早等表达需要规则化。

### 解决策略

第一版采用规则优先：

- 覆盖今天、明天、后天、下周。
- 覆盖上午、下午、晚上。
- 覆盖几点、几点半、十点半。
- 覆盖提前几分钟、几小时提醒。
- 默认事件时长为 1 小时。

解析不确定时不直接写入，而是追问：

- 「你说的是上午三点还是下午三点？」
- 「请问这个日程安排在哪一天？」

复杂表达可以后续交给 AI 接口增强，但不能让 AI 成为唯一方案。

### 验收标准

- 高频中文时间表达能解析正确。
- 不确定时间会追问。
- 写入前展示结构化时间供用户确认。

## 3. 难点二：Agent 意图识别

### 难在哪里

用户可能用不同说法表达同一个意图：

- 新增：「明天下午三点开会」「帮我安排一个会」。
- 查询：「我明天有什么安排」「看看下周日程」。
- 修改：「把产品会改到四点」「会议提前半小时」。
- 删除：「删掉明天那个会」「取消下午的会议」。
- 空闲查询：「明天下午我什么时候有空」。

系统必须判断用户到底要做什么操作。

### 解决策略

第一版定义有限意图集合：

```text
create_event
list_events
update_event
delete_event
find_free_time
set_reminder
confirm
cancel
undo
unknown
```

先使用关键词和规则匹配：

- 包含「安排、添加、创建、开会、提醒」倾向新增。
- 包含「查看、有什么、日程、安排」倾向查询。
- 包含「删除、取消、删掉」倾向删除。
- 包含「改到、提前、推迟、修改」倾向修改。
- 包含「有空、空闲」倾向空闲查询。

如果匹配不明确，则提示用户换一种说法或进入追问。

### 验收标准

- 常见指令能进入正确操作分支。
- 无法识别时不崩溃。
- 不把删除误识别成查询或新增。

## 4. 难点三：多轮对话状态机

### 难在哪里

真实用户经常不会一次说完整：

```text
用户：帮我约个会
Agent：请问安排在什么时候？
用户：明天下午三点
Agent：会议主题是什么？
用户：产品评审
Agent：是否确认添加？
```

这要求系统记住当前正在处理的任务，而不是把每一句话都当成独立指令。

### 解决策略

使用 `pendingAction` 保存未完成操作：

```ts
type PendingAction = {
  type: "create_event" | "update_event" | "delete_event";
  collectedFields: Record<string, unknown>;
  missingFields: string[];
  candidates?: CalendarEvent[];
  status: "collecting" | "confirming" | "conflict";
};
```

对话状态包括：

- `idle`：没有待处理操作。
- `collecting`：正在补充信息。
- `confirming`：等待用户确认。
- `selecting`：多个候选事件等待选择。
- `conflict`：发现时间冲突等待处理。

### 验收标准

- 用户补充信息后能接上上一轮上下文。
- 用户说「确认」时只确认当前 pending action。
- 用户说「取消」时清空当前 pending action。

## 5. 难点四：修改和删除的事件匹配

### 难在哪里

新增事件只需要创建，但修改和删除必须先找到目标事件。

用户可能说：

- 删除明天的会。
- 取消下午那个会议。
- 把产品会改到四点。
- 删除刚才那个安排。

如果匹配错误，会造成严重信任问题。

### 解决策略

事件匹配按优先级：

1. 当前选中的事件。
2. 最近一次创建或查看的事件。
3. 标题关键词匹配。
4. 日期时间范围匹配。
5. 多候选时让用户选择。

绝不直接删除多个候选事件。

删除必须二次确认：

```text
我找到了「明天下午三点 产品评审会」，确认删除吗？
```

修改必须展示前后差异：

```text
将「产品评审会」从 15:00 改到 16:00，是否确认？
```

### 验收标准

- 找不到事件时提示未找到。
- 多个候选时要求选择。
- 删除和修改不会静默执行。

## 6. 难点五：写操作安全机制

### 难在哪里

语音操作很方便，但误识别和误理解都会带来风险。

例如：

- 语音识别错标题。
- 时间解析错上午下午。
- 用户说「取消」可能是取消会议，也可能是取消当前操作。
- 删除不可轻易恢复。

### 解决策略

所有写操作都必须确认：

- 新增。
- 修改。
- 删除。
- 冲突情况下继续添加。

支持撤销最近一次操作：

- 撤销新增：删除刚创建的事件。
- 撤销删除：恢复刚删除的事件。
- 撤销修改：恢复旧字段。

### 验收标准

- 没有确认不写入。
- 删除必须二次确认。
- 最近一次操作可撤销。

## 7. 难点六：语音识别不稳定

### 难在哪里

浏览器语音识别可能出现：

- 浏览器不支持。
- 麦克风权限被拒绝。
- 中文识别错误。
- 环境噪音影响识别。
- 停顿导致提前结束。

### 解决策略

- 推荐 Chrome 演示。
- 识别结果放入文本框，允许用户修改。
- 保留文字输入完整能力。
- 语音不可用时提示原因。
- 语音播报失败不影响核心操作。

### 验收标准

- 麦克风不可用时应用仍可通过文字指令使用。
- 语音识别结果可编辑。
- 语音失败不会阻断日历功能。

## 8. 难点七：状态一致性

### 难在哪里

Agent 对话、日历列表、事件详情、本地存储必须保持一致。

常见问题：

- Agent 说添加成功，但日历没显示。
- 修改事件后出现重复事件。
- 删除事件后详情面板还显示旧事件。
- 刷新页面后事件丢失。

### 解决策略

- 统一事件数据源。
- 所有日历操作通过同一层 `eventStore`。
- 写操作完成后统一刷新派生视图。
- localStorage 写入成功后再反馈成功。
- 使用事件 id，而不是标题，作为内部唯一标识。

### 验收标准

- 事件增删改后所有视图同步。
- 刷新页面后数据仍存在。
- 修改不会创建重复事件。

## 9. 难点八：一天内范围控制

### 难在哪里

语音日历很容易扩展出很多功能：

- Google Calendar。
- Outlook。
- 用户登录。
- 云端同步。
- 后台管理。
- 周期日程。
- 多人会议邀请。
- 移动端 App。

这些都合理，但不适合第一天。

### 解决策略

第一版只做主闭环：

```text
语音 / 文字输入
-> Agent 解析
-> 用户确认
-> 日历 CRUD
-> 日历视图更新
-> localStorage 持久化
```

放弃或后置：

- 第三方日历同步。
- 登录和后台。
- 云数据库。
- 复杂周期事件。
- 邮件邀请。

### 验收标准

- 核心演示路径稳定。
- 不因非核心功能拖慢上线。
- 所有加分项都不影响主流程。

## 10. 难点优先级

| 优先级 | 难点 | 原因 |
| --- | --- | --- |
| P0 | 中文时间解析 | 直接决定日程是否正确 |
| P0 | 修改 / 删除事件匹配 | 直接决定用户信任 |
| P0 | 确认和撤销 | 防止误操作 |
| P0 | 状态一致性 | 决定产品是否可用 |
| P1 | 多轮对话状态机 | 提升 Agent 感 |
| P1 | 语音识别兜底 | 保证演示稳定 |
| P1 | 冲突检测 | 提升专业度 |
| P2 | AI 复杂解析 | 增强能力，但不能依赖 |
| P2 | 第三方日历同步 | 后续产品化能力 |

## 11. 答辩表达建议

可以这样总结项目难点：

> 这个项目的核心难点不是日历 CRUD，而是把中文口语中的时间、意图和上下文稳定转换成可信的日历操作。我们通过规则优先的中文时间解析、有限意图 Agent、多轮确认状态机、删除修改二次确认、语音失败兜底和本地持久化，保证一天内交付一个可上线、可演示、可信的语音日历工具。
